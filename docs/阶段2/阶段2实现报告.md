## 二、现在仓库里已经有什么？（骨架，不是终稿）

`project/product-requirement/specification.yaml` 里**已经有一份草稿**（阶段 0 放入），方便你对照看。核心结构如下：

### 2.1 三步流水线（本期 product-requirement）

| 步 | 名称 | 谁做 | 产物 | 人话 |
|----|------|------|------|------|
| 1 | 整理需求故事 | AI | `output/requirement-story.md` | 先把日志讲成「一件事」，再拆背景/要做/不做/摘录 |
| 2 | 提取用户故事 JSON | AI | `output/stories.json` | 变成「用户要…」+ 三层 + 来源原句 |
| 3 | 人工评审定稿 | 人 | `output/accepted.json` | 你确认或 revise，留 approved 和 revisions |

**导师方法落在哪：** 第一步强调「讲故事再结构化」——对应官方 product-requirement 的前两步思想，但 yaml 里**合并表述为「整理需求故事」再「提取 JSON」**。

**✅ 已拍板（2026-08-30）：保持 yaml 里 3 步，不再拆细。**  
理由：「先讲故事、再拆背景/摘录」是 Step1 **内部结构**（写在 `note` 和阶段 3 提示词里），不是多一道 Loop 工序。拆成 4 步会让 feedback 变多、dry-run 和 review 都对不齐；和官方「两步 AI + 一人确认」也不一致。

### 2.2 反馈点（人要停下来的地方）

| 在谁之后 | 问什么 |
|----------|--------|
| 整理需求故事 | 故事通不通？能进 JSON 吗？`ok` 或 `revise:…` |
| 提取用户故事 JSON | 有无编造/漏抓/分层错？`ok` 或 `revise:…` |

与阶段 0 `review.html` 的 ✓ / ✗ 是**同一套语义**，阶段 4 跑 Loop 时走 CLI 的 `ok` / `revise:编造:…`。

### 2.3 锁定与重跑（loop + locking 块）

草稿里写了：

- `revise` 只重跑**当前步**，不从头来  
- 已通过的可锁定（`output/locked/`、`approved=true`）  
- 快捷码：编造 | 分层 | 漏了 | 格式 | 其他  

**✅ 已拍板（2026-08-30）：yaml 写规则 + 阶段 4 代码强制执行，两步都要。**

| 写在哪 | 干什么 | 类比 |
|--------|--------|------|
| `specification.yaml`（`loop` / `locking`） | **合同**：人读得懂「应该怎样」 | 图纸上的「门要锁」 |
| `implementation.py`（阶段 4） | **执行**：真复制到 `output/locked/`、revise 只重跑当前步、跳过 `approved=true` | 施工队装门锁 |

阶段 2 只把 yaml 里的规则**写清楚、不自相矛盾**；**不会**在阶段 2 改 `implementation.py`。没有阶段 4 代码，yaml 只是一段说明，程序不会自动锁文件。

### 2.4 数值门槛（acceptance 块）

| 字段 | 目标值 | 含义 |
|------|--------|------|
| `fabrication_count` | 0 | 不许编造 |
| `source_quote_pass_rate` | 1.0 | 每条来源能在原文找到 |
| `sentence_coverage_rate` | 1.0 | 日志句子都要被覆盖到 |
| `feedback_triggered` | true | 至少走过一次人确认 |
| `min_rounds` | 1 | 至少跑一轮 |

**注意：** 这是**课题声明的门槛**；实测数字只写在 `trial-report.md`（阶段 6），不要和这里混。

### 2.5 本期刻意不做（写在 yaml 里也不实现）

| 项 | 原因 |
|----|------|
| 第 3 步「JSON→SQL」 | 官方 index 写了，本期 **deferred** |
| 产品云选日志 UI | 本期用文件 `journal-official-full.md` |
| 改 `implementation.py` 业务 | 阶段 2 只改 yaml 定义 |

## 三、为什么要和 devops-code 对齐？（图7）

官方已有一条成熟 Loop：`devops-code`。product-requirement **照同一套字段抄**，答辩时能说「和量潮范式同构」。

![图7 devops-code specification.yaml](../../screenshots/04-devops-code-spec.png)

| 字段块 | devops-code 有 | 我们草稿有 | 阶段 2 要确认的 |
|--------|----------------|------------|----------------|
| `name` / `description` | ✓ | ✓ | 名称是否叫 product-requirement |
| `entry` / `exit` | ✓ | ✓ | 入口是否写清「日志文件路径」 |
| `steps[]` | ✓ | ✓ | 三步 actor/artifact/check 是否够细 |
| `feedback[]` | ✓ | ✓ | 是否两步 AI 后各一个人工点 |
| `loop` | ✓ | ✓ | revise/锁定语义是否与 review.html 一致 |
| `metrics` | ✓ | ✓ | rounds/time/corrections/rework |
| `acceptance` | 部分有 | ✓ | 数值门槛是否导师认可 |
| `locking` | 可能无 | ✓（我们多加） | 是否保留为扩展块，或并入 `loop` |

**阶段 2 的工作：** 不是从零发明，而是 **对照图7 逐项勾**，缺的补、多的解释清楚。
