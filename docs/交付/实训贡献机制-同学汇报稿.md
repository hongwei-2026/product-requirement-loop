## 1. 一句话结论

我们用 **GitHub Issue + 评论命令 + Design 落库 + 实现 PR + Actions** 管理实训任务：谁接了、谁放弃、交什么材料、分数多少，都可审计；仪表盘自动同步。  
**硬性规则：同一 GitHub 账号同时只能接 1 个进行中任务**（要换题先 `/cancel`）。另有一批 **特难（Extreme）** 扩展题（#9–#22），对齐量潮下游资产、多人协作与可复现。

## 4. 标准流水（全员同一套）

```text
浏览任务 Issue（读正文规则）
        │
        ▼
评论（单独一行）：/claim
        │  → 仪表盘「进行中的认领」出现你
        ▼
写设计文档：docs/designs/#N-简短英文.md
开 PR：选择模板「Design」，标题 [Design] #N …
邮件 feizi_050920@qq.com（Issue + Design PR + GitHub ID）
        │
        ▼
维护者评论：/accept @你
        │  → 任务锁定；仪表盘变为「已锁定」
        ▼
开 PR：选择模板「Implementation」，标题 [Impl] #N …
正文：Fixes #N + 演示视频链接 + 截图≥2
        │  → CI + Enterprise 检查 + 四人 Approve
        ▼
合并后维护者：/score N
        │  → 计分板 / 仪表盘刷新
        ▼
完成
```

### 4.1 命令速查

| 命令 | 发在哪里 | 谁可以用 | 作用 |
|------|----------|----------|------|
| `/claim` | 任务 **Issue** | 登录用户 | 申请接取（**账号已有进行中任务则拒绝**） |
| `/accept @用户` | 任务 Issue | 仅维护者 | 正式锁定 |
| `/cancel` 或 `/release` | 任务 Issue | 认领人 / Assignee / 维护者 | 放弃；仪表盘**自动删除**认领记录 |
| `/reject-claim` | 任务 Issue | 维护者 | 强制清空别人的认领 |
| `/score N` | 任务 Issue | 维护者或必审人 | 记分（建议合并后再记） |
| `/recheck` | **PR** 评论 | PR 作者或必审人 | 重跑企业级检查套件 |

命令必须**单独成行**。同义复检：`/rerun`、`/rerun-checks`。

### 4.2 放弃会怎样？

- Issue **不会**被删除，只是清掉「谁在做」。  
- Assignee、认领标签清除，任务重新开放。  
- 仪表盘「进行中的认领」里该条**自动消失**。

## 5. Design 往哪交（重点强调）

以前容易只在评论里写方案——**现在必须落库：**

1. 从 `docs/designs/_TEMPLATE.md` 复制  
2. 存为 `docs/designs/#任务号-简短英文.md`（例：`#1-topbar-llm-summary.md`）  
3. GitHub 开 PR 时选模板 **Design**  
4. 正文用 `Related to #N`，**不要**用 `Fixes`（避免未实现就关 Issue）  
5. 发邮件给 `feizi_050920@qq.com`

流水 `Enterprise PR / design-gate` 会检查：本 PR 是否改到了对应 `docs/designs/#N-*.md`。

## 6. 实现 PR 交付三件套（缺一不可）

全部写在 **PR 正文**（模板选 **Implementation**）：

| # | 交付物 | 要求 |
|---|--------|------|
| 1 | **代码** | `Fixes #N`；作者必须是已 `/accept` 的 Assignee |
| 2 | **演示视频链接** | 可公网打开（B 站 / 飞书云文档·妙记 / 录屏分享等） |
| 3 | **截图 ≥ 2 张** | 改前/改后或关键成功界面，直接贴图 |

- 流水 `delivery-artifacts` 会自动检测视频 URL 与截图数量。  
- 缺材料 → 检查红灯；审核员应 Request changes，补齐后评论 `/recheck`。  
- 截图 / 视频中禁止出现 API Key。

## 7. 企业级自动检查（人多时靠流水）

开 PR 或评论 `/recheck` 后，会跑 **Enterprise PR** 套件，主要包括：

| 检查 | 作用 |
|------|------|
| classify | 自动打 `type:design` / `type:implementation` |
| delivery-artifacts | Impl：视频+截图；Design：设计文档章节 |
| design-gate | Design 必须落在 `docs/designs/#N-*.md` |
| scope-guard | 超大 PR / 乱改 workflows 拦截 |
| task-lock | 实现须已锁定且作者正确 |
| suite-summary | PR 下粘性状态评论 |

此外还有：

- **CI**：仓库级 `verify_*`、密钥扫描、安全门禁等  
- **Required reviewers**：四位必审人全部 Approve  
- **Task board**：Issue 上的 `/claim` 等命令与仪表盘同步  

推送新 commit 后，旧 Approve 可能作废，需再审一次。

## 8. 给审核同学（30 秒）

1. 打开独立文档：[审核员指南.md](./审核员指南.md)  
2. 先看 Checks 是否绿、PR 正文有无视频与截图  
3. 再看 diff 是否对准 Issue / Design，有无破坏门禁  
4. 缺材料 → 不要 Approve；写清要补什么，让对方 `/recheck`

## 9. 安全红线（全员）

- 禁止把 API Key、Token、私钥写进代码、Issue、截图、视频、评论  
- 本地密钥只放 `project/.env`（已 gitignore）  
- 不要绕过登录、本机绑定、Step3 check 门禁、待审库取消能力  
- 未 `/accept` 抢写实现 PR → `task-lock` 会拦，不算有效交付

## 10. 口头汇报可用提纲（约 2 分钟）

1. **背景**：人一多需要统一接任务和审查，不能靠口头。  
2. **机制**：Issue 认领 → Design 落 `docs/designs/` → 邮件 → `/accept` → 实现三件套 → 四人审 → 计分。  
3. **仪表盘**：认领、放弃、得分会自动反映。  
4. **流水**：交付物、设计位、锁定、体量都有企业级检查；红了就 `/recheck`。  
5. **分工**：同学看《任务贡献指南》，审核员看《审核员指南》。  
6. **行动**：从 [#7](https://github.com/hongwei-2026/product-requirement-loop/issues/7) 选任务，读 Issue 正文后 `/claim`。
