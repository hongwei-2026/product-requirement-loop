本机制用 **GitHub Issue + 评论命令 + Design PR + Implementation PR + Actions** 管理贡献，适合实训接任务、防抢单、可审计计分。

## 一、总流水（每个任务相同）

```text
浏览任务 Issue（带难度/积分）
        │
        ▼
评论区发送：/claim
        │  ← Actions 机器人回复「请写设计 PR + 发邮件」
        ▼
提交 Design PR（标题含 Design / #Issue号）
并把「设计PR链接 + Issue链接 + 你的 GitHub ID」
发到邮箱 feizi_050920@qq.com
        │
        ▼
维护者审核设计后，在你的 /claim 评论下回复：
/accept @你的用户名
        │  ← 只有 hongwei-2026 的 /accept 生效；Issue 锁定指派给你
        ▼
实现代码，开 Implementation PR（Fixes #号）
        │  ← CI + 任务门禁 + 自动审核清单
        ▼
维护者/审阅人 Code Review，合并后评论：
/score <分>
        │
        ▼
计分板更新；任务关闭
```

## 二、评论命令（必须原样写在 Issue 评论区）

| 命令 | 谁可以发 | 作用 |
|------|----------|------|
| `/claim` | 任意登录用户 | 申请接取；机器人回复下一步（设计 PR + 邮件） |
| `/accept @username` | **仅 hongwei-2026** | 正式把任务锁定给该用户（须已 `/claim`） |
| `/reject-claim` | 仅 hongwei-2026 | 拒绝申请，清空认领 |
| `/release` | 被指派者或 hongwei-2026 | 放弃任务，重新开放 |
| `/score N` | hongwei-2026 或带 `reviewer` 的协作者 | 记 N 分到计分板（通常在实现合并后） |

> 命令单独成行，前面不要加其它字符。例如整行只有：`/claim`

## 三、设计 PR 要求（Design）

1. 从 `main` 开分支：`design/#<issue>-简短英文`  
2. PR 标题：`[Design] #<issue> 简要标题`  
3. PR 正文必须包含：

```markdown
## 关联 Issue
Closes nothing yet / Related to #<issue>

## 方案摘要
（要改什么、为什么、不改什么）

## 影响面
- 文件/模块：
- 对现有 check 门禁 / CI 的影响：

## 验收标准
- [ ] …

## 风险
…
```

4. **不要在 Design PR 里塞完整实现**（可放伪代码/接口草图）。  
5. 发邮件主题建议：`[Design] #<issue> <你的GitHubID>`  
   正文附：Issue 链接、Design PR 链接、GitHub ID。

---

## 四、实现 PR 要求（Implementation）

1. 分支：`feat/#<issue>-简短英文`  
2. 标题：`[Impl] #<issue> 简要标题`  
3. 正文必须有：`Fixes #<issue>`（或 `Closes #<issue>`）  
4. 作者必须是 Issue **Assignee**（已被 `/accept` 锁定的人），否则任务门禁 Workflow 会失败。  
5. 通过 CI：`verify_docs_layout` / `verify_lessons` / `verify_security` 等。  
6. 自动「AI 审核助手」会在 PR 下贴检查清单；人工审核通过后再合并。

---

## 五、难度与默认积分

| 难度 | 标签 | 默认积分 | 说明 |
|------|------|----------|------|
| 简单 | `difficulty:easy` | 10～15 | 文案/展示/小交互，触及面小 |
| 中等 | `difficulty:medium` | 25～35 | 单模块功能，需设计与自测 |
| 难 | `difficulty:hard` | 50～60 | 架构/异步/压测流水，回归面大 |

具体分数以 Issue 正文「积分」字段为准；`/score` 可按完成质量微调。
