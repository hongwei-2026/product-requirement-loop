## 二、评论命令（必须原样写在 Issue 评论区）

| 命令 | 谁可以发 | 作用 |
|------|----------|------|
| `/claim` | 任意登录用户 | 申请接取；写入仪表盘「进行中」 |
| `/accept @username` | **仅 hongwei-2026** | 正式锁定给该用户 |
| `/cancel` 或 `/release` | 当前认领人 / 受指派人 / 维护者 | **放弃任务**：清 Assignee、清标签，并从仪表盘**自动删除**认领记录 |
| `/reject-claim` | 仅 hongwei-2026 | 强制清空别人的认领（效果同放弃） |
| `/score N` | hongwei-2026 或必审人 | 记分并刷新排行榜 |

> 命令单独成行。例如整行只有：`/claim` 或 `/cancel`。

### 接了任务后，仪表盘怎么同步？

| 动作 | 仪表盘变化（Actions 自动 commit） |
|------|-----------------------------------|
| 有人 `/claim` | 「进行中的认领」出现该 Issue + 用户 |
| 你 `/accept @他` | 状态变为「已锁定实现中」 |
| 他 `/cancel` 或 `/release` | 该条**自动删除**，任务变回开放 |
| `/score N` | 排行榜加分；认领标成已完成 |

看这里：[`任务仪表盘.md`](./任务仪表盘.md) · [`docs/dashboard/index.html`](../dashboard/index.html)

## 三、设计 PR 要求（Design）

1. 从 `main` 开分支：`design/#<issue>-简短英文`  
2. PR 标题：`[Design] #<issue> 简要标题`  
3. PR 正文必须包含：

```markdown
## 关联 Issue
Closes nothing yet / Related to #<issue>

## 方案摘要
（要改什么、为什么、不改什么）

## 影响面
- 文件/模块：
- 对现有 check 门禁 / CI 的影响：

## 验收标准
- [ ] …

## 风险
…
```

4. **不要在 Design PR 里塞完整实现**（可放伪代码/接口草图）。  
5. 发邮件主题建议：`[Design] #<issue> <你的GitHubID>`  
   正文附：Issue 链接、Design PR 链接、GitHub ID。

## 四、实现 PR 要求（Implementation）

1. 分支：`feat/#<issue>-简短英文`  
2. 标题：`[Impl] #<issue> 简要标题`  
3. 正文必须有：`Fixes #<issue>`（或 `Closes #<issue>`）  
4. 作者必须是 Issue **Assignee**（已被 `/accept` 锁定的人），否则任务门禁 Workflow 会失败。  
5. 通过 CI：`verify_docs_layout` / `verify_lessons` / `verify_security` 等。  
6. 自动「AI 审核助手」会在 PR 下贴检查清单；人工审核通过后再合并。  
7. **交付物三件套（缺一不可，写在 PR 正文，勿只评论）**：
   - **代码**（本 PR）
   - **演示视频链接**（可公网打开：B 站 / 飞书云文档·妙记 / 录屏分享等，展示完整操作）
   - **截图 ≥2 张**（改前/改后或关键成功界面，直接贴图）
8. 视频/截图中禁止出现 API Key；缺材料时必审人可拒 Approve。

> 接取/放弃说明也应写在 **Issue 描述正文**（见 [任务Issue标准块.md](./任务Issue标准块.md)），不要只靠机器人评论。

## 五、难度与默认积分

| 难度 | 标签 | 默认积分 | 说明 |
|------|------|----------|------|
| 简单 | `difficulty:easy` | 10～15 | 文案/展示/小交互，触及面小 |
| 中等 | `difficulty:medium` | 25～35 | 单模块功能，需设计与自测 |
| 难 | `difficulty:hard` | 50～60 | 架构/异步/压测流水，回归面大 |

具体分数以 Issue 正文「积分」字段为准；`/score` 可按完成质量微调。
