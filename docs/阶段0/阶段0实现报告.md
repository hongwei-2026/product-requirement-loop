## 二、故事继续：产品云到底要什么？（非专业版）

### 2.1 用一句人话

**产品云希望：** 把研发日志里的乱话，整理成一张「谁要什么」的清单，并且每条都能指回日志原句，人改完再定稿。

对应官方 **图1**（`qtcloud-product/requirement.md`）：

![图1 产品云：捕捉用户故事](../../screenshots/13-product-cloud-capture.png)

### 2.2 名词解释（看不懂术语就看这里）

| 术语 | 人话 |
|------|------|
| **研发日志** | 同事每天写的研发记录，在 GitHub 仓库 `quanttide-journal-of-product-development` |
| **零碎话语** | 日志里口语化、不整齐的句子 |
| **用户故事** | 用「**用户要……**」写的需求，例如「用户要选择日志来源」 |
| **activity / task / story** | 三层粗细：大事 → 中事 → 小事（官方中文：活动 / 任务 / 故事细节） |
| **AI 辅助** | AI 先起草 |
| **人调整** | 你觉得不对就改，改完再确认 |
| **来源依据** | 每条需求旁边注明「这句话来自日志哪一句」 |
| **Loop** | 带「停一下让人确认」的流水线，不是 AI 一次性糊完 |

### 2.3 为啥是 activity / task / story 三层，不是别的？

**不是我发明的。** 产品云需求文档和 `requirement.json` 就这么组织的。

**图5** 官方 JSON 结构：

![图5 requirement.json](../../screenshots/12-requirement-json.png)

**合理性（官方语境）：**

- **活动**：一大块工作，如「需求梳理」  
- **任务**：活动下的步骤，如「捕捉用户故事」  
- **故事细节**：具体到「用户要…」的一条条  

这就像：**章节 → 小节 → 要点**。产品云后面要画「用户故事地图」，地图本身就是按这三层铺的（图10）。

![图10 划分层级与人工调整](../../screenshots/10-product-cloud-stories.png)

如果不用这三层，就和官方 `requirement.json`、故事地图对不上——**后期接产品云会卡住**。所以本期对齐官方，不另起分层。

### 2.4 本期做两步，你怎么验收？

官方 Loop 有三步；本期只做前两步。小王记了三个口令：

| 步 | 产出 | 你怎么验 |
|----|------|----------|
| 1 | `requirement-story.md` | 读一遍：像不像在讲「一件事」？有没有「原文摘录」？ |
| 2 | `stories.json` | 打开 `review.html`：左边原文、右边故事，来源原句能不能对上？ |
| 人确认 | `accepted.json` | 有你的勾选记录；打叉的须写原因 |

另外四条规矩（你说得对，验收不能含糊）：

1. 每一步必须在 `review.html` 打勾，或打叉并写一句原因  
2. 每条故事必须有「来源原句」  
3. `check.py` 全绿才算这一步过了  
4. 结论写在 `trial-report.md`，不口头说「应该没问题」

### 3.2 「用户要选择日志来源」——你咋选？

在官方体系里，「选来源」= **选哪个产品流文件夹 + 哪天的 md 文件**。

本期 case-01 已替你选好（有理由）：

| 选择项 | case-01 的选择 | 为什么 |
|--------|----------------|--------|
| 产品流 | `qtcloud-product/` | 与产品云需求直接相关 |
| 日期 | `2026-08-19.md` | 文中直接讨论「从日志捕捉用户故事」 |
| 段落 | 见 `journal-raw.md` | 与图1 官方需求同构 |

**你以后自己选：** 在同一仓库里换另一个 `qtcloud-*/YYYY-MM-DD.md`，更新 `SOURCE.md` 即可。

### 3.3 AI 怎么捕捉用户故事？信息对吗？是我们要的吗？

**分工（官方 + 本期设计）：**

| 环节 | 谁做 | 你怎么判断对不对 |
|------|------|------------------|
| 从乱话里找候选句 | **AI 先找** | 在 review.html 对照原文 |
| 写成「用户要…」 | **AI 先写** | 看是否以「用户要」开头 |
| 分 activity/task/story | **AI 先分** | 看分层是否讲得通 |
| 定稿 | **人确认** | 你在 review.html 打勾或 revise |

**捕捉错了怎么办？**  
不硬认。你写 `revise: 第三条分层错了，应该是任务不是故事`，Loop 重跑该步。这就是「人调整」。

### 3.4 「用户要先捕捉出格式」——不是 AI 找吗？

官方原话是 **「用户要……」** 句式，意思是：**最终呈现给产研负责人的条目必须是这种格式**。

实际执行：

1. **AI** 从日志提取并改成「用户要…」  
2. **人** 看格式对不对、内容对不对  
3. **人** 点通过，才写入 `accepted.json`

所以：**AI 找 + 人确定**，不是纯 AI 一把梭，也不是纯人工抄。

### 3.5 如何复核更准确？（给你可操作步骤）

打开 `project/trials/case-01/review.html`，按顺序做：

1. **找得到：** 每条「来源原句」在左边原文里 Ctrl+F 搜索，必须能搜到  
2. **没多加：** 右边如果出现左边完全没提到的功能，打回 revise  
3. **没漏抓：** 左边你认为重要的句子，右边至少有一条能覆盖（用 `check.py` 算覆盖率，标准是 100%）  
4. **分层合理：** 问自己「这是大事、步骤，还是一条具体需求？」  
5. **打勾留痕：** 勾选页面底部 4 项，写复核人和日期
