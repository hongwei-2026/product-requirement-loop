对你比如说，你像 DeVos 云，那么如果想要让它顺畅的话，那么可能比较好的办法就是：

先把 GitHub 的仓库同步到 GitLink 上，然后只做“已读”功能，把各种发布信息之类的信息全部集中到 DeVos 里面。

这倒不失为一种好的策略，它能够极大程度上减少在去中心化的模式之下看不到信息的问题。这个策略应该是可行的。

现在能做这个事情，是因为仓库足够多，它们之间的关系开始变得复杂。那么在这个时候，引入这种观测工具其实不失为一种好办法，让我们能够看到整个系统的迭代进展如何。

服务端本质上其实是一个缓存。如果我想要知道最新情况，就还是得更新一下看看：
1. 如果仓库有更新，我就去拉取一下，看看各个 scope 更新得怎么样，把这个信息整理下来。
2. 如果没有更新，说明我数据库里的数据还是对的，直接返回就可以。

这其实就已经构成了一个基本的事件 l 申报工作流了。

这样的话，相比于命令行，它更多的是一个端测工具。那么服务端和客户端最新的功能，就可以多往这个观测上去走。

命令行也可以跟着逐步去改造，让它具备一些观测功能。比如：
1. 把像 status 这种信息跟云端接上；
2. 让它跟本地仓库进行一定程度的同步。

但是说实话，这个蛮复杂的，因为这会涉及到本地，还有你的仓库员到底以谁为事实员的问题。首先得能同步成才可以，反正这里面就会增加很多细节问题。

这些问题不能过早地去设计状态机。我一开始为你们设计状态机失效的原因，是因为根本不知道这个状态机在整个地图之中的功能到底是什么。如果你贸然接一个进去，可能这个状态被定义了，但它跟全局没有关系，就会导致你根本启用不了这个状态。这是我早期一些设计失败的主要原因。
