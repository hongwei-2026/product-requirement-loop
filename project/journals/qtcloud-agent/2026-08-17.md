我试了一下换模型，就发现换模型的过程之中问题百出，各种模型不一样。

因为各个版本老是在变，所以影响其实也比较大。如果能统一记录一下这个信息，可能会有帮助。

我觉得一个比较重要的需求是，我们现在有很多智能体，需要去治理它们。这个治理主要包括：
1. 评估它们在各个方面的好用程度；
2. 明确什么任务该用什么智能体；
3. 特别是治理它们产生的数据，这是关键点。

也就是说，智能体在持续观察其他智能体的过程中，建立了一个类似“观测站”的东西。我们应该将其定义为“智能体的观测站”，先观测，然后再提高。

你可以通过对话本身去分析：
1. 这个智能体为什么做得好，为什么做得不好；
2. 我们要怎么去提升这个智能体的效果；
3. 从一些共同的地方去分析，比如对话怎么分析等等。

因为我发现小米的 MIMO 其实分析对话的能力挺强的，再加上它的价格依然是最便宜的一个，所以用它就比较合适。

在这个环节，我们可以让更多的分析工作由小米 MIMO 去做；而执行工作，也就是更多前台的、偏理科的、一些行动性的工作，让 DeepSeek 去做。这样，我们依然可以形成一个分层。

在这个过程中，我们首先要面临的一个摩擦，就是不同的智能体有不同的设计结构。

其实我对于文档和源码都没有那么熟，不像以前那么熟悉，因为现在看东西基本上不怎么去用它。但是这也是很容易补的，我们可以通过各种各样的方式重新再找一遍就可以了。

对，比如 session，也就是 message history 这样的东西，它是目前大家最常见的一个基础，可以从这里开始治理起。我们也知道用它会有更好的效果，比如分析可能会分析出更好的效果。通过它去不断地观测智能体，因为观测的过程，其实也就是我们去找到自己需要优化的地方。

再上一个层次，比如说各种 skill；再上一个层次就是各种 harness、各种 loop 之类的。

它其实是一个非常理想的分层结构，像字节做的 AI Agent 数据湖，就是很好的参考资料。

不过，我们更激进一点，把这些结构化的东西都放进去了。正好 DeepSeek 也有非常好的生态，我们可以把 harness 的 plugin 放在最上层，其他的 plugin 也可以对标。我们可以把插件分析本身作为一个 harness 的机制。

对，在工程上，我们选择一个智能体先开始就可以。比如，如果想要追市场热点，就可以先选 DSH 去分析它的存储结构。

像我们常用的，比如 PI、harness 这些，都可以去了解一下，知道它的结构是什么样的，优点和缺点在哪里，通过分析了解它的情况等等。

因为我也发现，如果我尝试让 AI 去解析对话，它就要找半天。这意味着我们可以通过一个更标准的工具，更方便地进行端测分析。这其实就是智能体云命令行工具的主要作用。当然，客户端也可以做端测，没什么区别。
